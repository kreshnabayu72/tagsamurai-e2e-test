# Konvensi E2E Automation (sumber PRD) — TAG Samurai

Dokumen ini khusus untuk alur kerja bersumber PRD (skill `e2e-prd-generate-spec` dan `e2e-prd-audit`): spec dibuat langsung dari PRD inti modul, tanpa TC granular di antaranya. Alur bersumber TC tetap memakai `docs/e2e-conventions.md`, yang tidak diubah oleh dokumen ini.

Aturan framework TestSpectra (satu `it()` per file, zero-import, suffix platform, dan seterusnya) ada di skill bawaan `.claude/skills/*` dan tidak diulang di sini. Dokumen ini hanya memuat aturan khusus TAG Samurai.

**Peta baca per peran `[KEPUTUSAN 2026-11-03]`:** baca hanya bagian yang dibutuhkan peran Anda.
- Penyusun rencana (planner, generate sampai gate approval rencana): bagian 2, 3, 3a, 5, 6, paragraf ID spec bagian 7, 8, 10, 10a, 11, dan butir Lampiran A modulnya. Bahan bacanya rules JSON, indeks aturan, matriks role PRD §2, blok Example Data §4.1.x, daftar ditahan, dan baris PRD mentah per rentang ID bila perlu; bukan PRD penuh.
- Penulis spec (writer, sesudah rencana disetujui): baris K-1 bagian 2, bagian 3 (prinsip 13 beserta pengecualian P-1 sampai P-12, Smell, dan Alasan wajib), 3a hanya untuk spec Role Matrix, 4, 5, 6, 7, 8, 8a, 8b, butir pertama bagian 9 (label tombol), 10, 10a, 11, dan butir Lampiran A modulnya. Bahan bacanya potongan rencana, baris aturan yang dikutip spec-nya, dan `docs/data/<Suite>.md`.
- Auditor: seluruh dokumen kecuali butir kedua sampai terakhir bagian 9 bila suite belum punya `web.test.ts`; dari Lampiran A hanya butir modulnya. Keterlacakan PRD → spec tidak diturunkan ulang oleh auditor (bagian 11 butir a).

Tanda `[VERIFIED]` = sudah dicek ke linter/CLI. Tanda `[REKOMENDASI]` = keputusan desain yang belum teruji di `spectra run` dan bisa diubah.

## 1. Alur Kerja

```
PRD inti <modul>.md (+ rules JSON work-items/<id>/rules-e2e-prd.json, dihitung harness)
   -> plan: aturan -> spec, data uji, Di luar E2E, Ditahan     skill: e2e-prd-generate-spec (gate approval)
   -> spec.md (+ sourceRules), docs/data/<Suite>.md, docs/coverage/<Suite>.md
   -> python scripts/check-suite-prd.py + spectra lint --strict  (wajib bersih sebelum generate selesai)
   -> e2e-prd-audit                                              (script T1-T10 + judgment per slice)
```

Sesudah audit, tahap script tetap sama dengan alur lama: `web.test.ts`, Page Object, Step, dan Fixture lewat skill `tagsamurai-e2e-generate-script`, lalu `spectra lint` dan `spectra run`.

Sumber kebenaran adalah **PRD inti modul** (`<modul>.md`, satu file). Spec e2e adalah turunan. Perubahan perilaku dilakukan di PRD dulu (lewat `prd-internal-gap-check`, `prd-gap-solve`, atau workflow PRD lain), baru disinkronkan ke spec; spec tidak pernah menambal PRD. Companion `<modul>.changelog.md` dan `<modul>.resolved.md` tidak pernah dibaca, dikutip, atau di-hash oleh alur ini.

Prasyarat (diperiksa harness sebelum generate dan audit): PRD satu file (PRD legacy folder `PRD/` ditolak sampai dimigrasi), sudah melewati `prd-audit-ready-refactor` (ID aturan atomik dan Indeks Item Teruji), dan state `prd-internal-gap-check` untuk PRD saat ini sudah ada. Harness menulis daftar aturan lengkap ke rules JSON: ID, jenis, induk, leaf atau bukan, prioritas warisan, caseType, status `held`, dan hash baris. **Penulis dan auditor tidak pernah mengarang ID aturan**; semua ID di spec, data uji, dan halaman coverage berasal dari rules JSON.

Istilah: **aturan** = ID aturan leaf di rules JSON (ID asli atau sintetis, bagian 8); **klausa** = satu pernyataan dalam teks aturan yang bisa gagal sendiri (S-01); **blok aturan** = langkah-langkah di bawah satu subjudul `### <ID aturan>: <judul pendek>`.

## 2. Seleksi Aturan: Dokumen E2E Merangkap TC FE `[KEPUTUSAN 2026-11-03]`

Dokumen per submodul ada tiga: **PRD inti** (`<modul>.md`, sumber semua aturan), **TC BE** (`tc-[modul]-backend.md`, kasus API langsung yang tetap dipelihara), dan **TC E2E** (kumpulan `spec.md` di repo ini). Spec e2e merangkap dokumen TC FE: tidak ada `tc-[modul].md` atau `tc-[modul]-frontend.md` di antara PRD dan spec, dan integration test FE (API di-mock, di repo FE) memakai `spec.md` sebagai acuannya.

- **K-1, cakupan aturan `[KEPUTUSAN 2026-11-03]`:** setiap aturan leaf di rules JSON berada di tepat satu kelompok: dikutip `sourceRules` sedikitnya satu spec, tercantum di tabel "Di luar E2E", atau tercantum di tabel "Ditahan" halaman coverage (bagian 8); satu aturan boleh dikutip beberapa spec, dan `sourceRules` sebuah spec memuat setiap aturan yang diasersi spec itu (tidak ada `Verifikasi` tanpa aturan sumber, kecuali anchor dan pembanding menurut S-03).

**Masuk spec (semua aturan yang terjangkau UI atau kemampuan uji yang dinyatakan):**
1. Aturan yang efeknya harus dibuktikan dengan backend dan data nyata: cascade, persistensi, integritas satu record, data lintas layar atau modul (spec FE+BE).
2. Aturan yang perilakunya di browser: tampilan teks dan state, tooltip, state disabled, hover, keystroke, Setup Column, retensi state (spec hanya-FE, atau langkah tambahan di spec FE+BE bila murah).
3. Kegagalan server (500, timeout), race, dan perubahan izin di tengah aksi, termasuk yang butuh pemicu khusus. Kalau dipicu lewat mock, masuk spec hanya-FE (`Mode: mock`). Kalau bisa dipicu di backend nyata, masuk spec FE+BE.
4. Kasus murah: menambah sekitar 2 langkah di alur yang sudah ada (contoh: jalur Cancel sebelum Confirm, guard tombol disabled).
5. Aturan defense-in-depth yang klausanya berupa respons API (status respons dan state data lewat fixture BE, kelas a prinsip 13) tetap masuk spec FE+BE walau isinya tumpang tindih dengan `tc-[modul]-backend.md`; aturan itu dikutip spec dan tidak dicantumkan di "Di luar E2E".

Spec dibagi menurut **mode eksekusi**, karena persiapannya berbeda:
- **Spec FE+BE:** dijalankan TestSpectra terhadap backend nyata, dengan data seeding di backend.
- **Spec hanya-FE:** dijalankan tim FE sebagai integration test dengan API di-mock (kasus 500, timeout, payload izin, tampilan murni). Ditandai dengan baris `Mode: mock` di `## Prerequisites`. Kebutuhan mock (respons apa yang dipaksa, di endpoint mana) ditulis di Prerequisites juga.

Spec hanya-FE dikelompokkan per layar atau topik UI (contoh: "Setup Column", "Tooltip dan disabled state", "Foto profil: hover dan staged", "Custom Field: input"), bukan satu spec per aturan dan bukan satu spec raksasa.

**Kelayakan teknis bukan kriteria seleksi `[KEPUTUSAN 2026-09-28]`:** kita menulis spec untuk apa yang seharusnya diuji, dan sengaja mendorong tim FE mengusahakan agar aturan itu bisa diuji otomatis (dua sesi browser, simulasi hardware, akun entity khusus, mailbox uji, dan sebagainya). Semua kebutuhan (data, akun, kondisi environment, dan kemampuan teknis yang diminta) ditulis di `## Prerequisites`, yang menjadi sumber resmi bagi tim FE. `## Notes` hanya penjelasan tambahan dan tidak boleh menjadi satu-satunya tempat sebuah kebutuhan tercatat. Kalau akhirnya tidak bisa, spec ditandai `coverage.web: unsupported`, bukan dihapus. Tim FE yang menyiapkan environment-nya.

**Di luar E2E:** aturan yang tidak dapat diotomasi e2e masuk tabel "Di luar E2E" halaman coverage dengan alasan dan rujukan case tc-backend bila ada (bagian 8). Hanya tiga alasan yang sah:
- Perilaku murni server yang tidak terjangkau UI dan tidak teramati lewat kemampuan baca BE (validasi kontrak API, logika internal server, job tanpa surface).
- Visual yang tidak dapat diasersi secara deterministik (warna, piksel, animasi, kesan tata letak). Teks, state, tooltip, dan keberadaan elemen bukan visual dalam arti ini dan tetap masuk spec.
- Lintas sistem: efek di sistem lain yang tidak dapat diamati dari aplikasi uji maupun harness uji (mail-catcher, simulator, fixture BE).

**Butir "Klausa di luar E2E" di `## Notes` spec `[KEPUTUSAN 2026-11-03]`:** ditulis "Klausa di luar E2E: <ID aturan> (<klausa>)" dan hanya sah untuk klausa dari aturan yang tetap dikutip spec dan efeknya perilaku murni server (alasan pertama di atas). Tiga hal bukan alasan sah: (a) klausa yang dimiliki aturan ditahan atau celah PRD (teks atau jalur tidak dinyatakan) ditulis sebagai butir "Temuan PRD", aturan penahannya masuk "Ditahan"; (b) hambatan data atau akun menjadi baris `DU-nn` dan langkah nyata; (c) alasan urutan commit atau race, karena efeknya teramati lewat klien HTTP dan fixture BE. Klausa yang bukan klausa aturan mana pun tidak ditulis. `check-suite-prd.py` T10 menampakkan butir tanpa ID aturan, dengan aturan yang tidak dikutip spec itu, atau beralasan hambatan data, akun, atau celah PRD.

**Ditahan:** aturan berstatus `held` di rules JSON (disentuh temuan terbuka `prd-internal-gap-check`, mis. `IGAP-0012`, atau temuan dependensi `DEP-n`) tidak ditulis ke spec dan dicantumkan di tabel "Ditahan" beserta temuannya. Aturan yang menurut penulis ambigu atau kontradiktif ditahan juga (S-15). Aturan lain dalam modul tetap ditulis. Aturan keluar dari "Ditahan" pada run berikutnya sesudah temuannya ditutup di PRD.

**K-2, kewajiban turunan `[KEPUTUSAN 2026-11-04]`:** rules JSON memuat tiga lapis selain aturan ber-ID PRD, agar suite sama lengkap dengan alur yang memakai TC tanpa ada TC: (1) baris matriks dan butir UI standar PRD (`<PFX>:<section>/<baris>`: UI Visibility per Role, Action Visibility, Global Table Rules, Defaults & Ordering, Action Resilience, Sync Matrix, Data Visibility, Plan Gating, Component States, Interaction Patterns, Aksesibilitas, Mobile Layout); (2) kewajiban uji yang diturunkan dari struktur PRD menurut pilar `foundation/testcase-conventions.md` P0 sampai P21 (`<PFX>:obl/<surface>/<kewajiban>`, `obligation: true`): per tabel Setup Column screening, format sel, Search, Filter, dan Sort per kolom, siklus Search, Filter Panel, siklus dan urutan default sort, Setup Column (sembunyikan, geser, reset, pin, kolom curated), Pagination, Download, klik, hover, dan nilai kosong per kolom; per heading `Page:` screening, F5, dan klik ulang menu; per heading `Modal:` screening, keyboard, form kotor, dan klik ganda Submit; per dialog `D-nn` bertombol `[Cancel]` penutupan tanpa efek; (3) aturan ber-ID PRD seperti biasa. Katalog dan pemetaan pilar: `prd-harness/.harness/reference/e2e-prd-obligations.md`. Lapis 1 dan 2 diperlakukan seperti aturan leaf (K-1): dikutip spec, "Di luar E2E", atau "Ditahan". Isi yang diasersi untuk kewajiban turunan diambil dari baris PRD yang ditunjuknya (kolom Setup Column, §5, §9.5) dan dari bagian `prd-conventions.md` yang dirujuk PRD (`refs` di rules JSON); kewajiban turunan tidak pernah mengarang perilaku yang tidak dinyatakan keduanya.

**Tidak berlaku `[KEPUTUSAN 2026-11-04]`:** kewajiban turunan (`obligation: true`, hanya lapis 2) yang dikesampingkan PRD sendiri (mis. tabel tanpa Pagination karena PRD membatasi jumlah baris, tabel read-only tanpa Download) dicantumkan di tabel "Tidak berlaku" halaman coverage dengan rujukan baris `L<n>` atau § PRD yang menyatakannya (T11). Aturan PRD (lapis 1 dan 3) tidak pernah "Tidak berlaku". Kewajiban yang PRD-nya diam bukan "Tidak berlaku": tulis spec dengan perilaku `prd-conventions.md` yang dirujuk, atau tahan dengan Temuan PRD (S-15).

**Tidak masuk spec selain kelompok di atas:** tidak ada. Permutasi data yang tidak menambah alur baru digabung (bagian 3); itu penggabungan, bukan pengecualian: aturannya tetap dikutip `sourceRules`.

**Klausa global:** klausa foundation (mis. `prd-conventions.md`) yang dirujuk PRD modul diasersi di bawah aturan PRD yang merujuknya. ID foundation tidak masuk `sourceRules`; hanya ID dari rules JSON yang dikutip.

**Hambatan teknis bukan alasan mengeluarkan aturan:** data, akun, waktu, kuota, race, kegagalan server, hardware, atau konfigurasi khusus tidak pernah menjadi alasan "Di luar E2E". Kebutuhannya ditulis di `## Prerequisites` dan tim FE yang menyiapkan environment.

**Data destruktif di environment automation:** environment yang dipakai run e2e adalah environment yang disiapkan dan diisolasi tim FE khusus untuk automation, bukan environment yang dipakai tester manual bersamaan. Karena itu, aksi Delete, Deactivate, atau Activate massal lewat Select All boleh dikonfirmasi sungguhan atas seluruh hasil Select All, termasuk saat kondisinya sengaja dibuat campur (banyak user, tersebar lintas halaman, status berbeda-beda) untuk menguji perilaku Select All itu sendiri (contoh: total `{N}`, exclude Default User dan Self, toggle ke Unselect All). Data yang dipakai tetap harus data uji milik automation (bagian 5), dicatat di Prerequisites.

**Pencatatan lapisan:** halaman `docs/coverage/<Suite>.md` mencatat tiap aturan ke spec beserta Mode (`FE+BE` atau `mock`), aturan "Di luar E2E" beserta rujukan tc-backend, dan aturan "Ditahan" (format persis di bagian 8).

## 3. Efisiensi: Pengelompokan Spec `[KEPUTUSAN 2026-09-28]`

Prioritas utama adalah efisiensi run. Framework memaksa satu `it()` per file spec, jadi satu spec = satu alur yang bisa dijalankan sekali jalan. Soft assertion (assert gagal tidak menghentikan spec) dan report per langkah tersedia (dikonfirmasi tim, belum saya uji sendiri). Unit penyusun spec adalah blok aturan.

**Prinsip pengelompokan:**
1. **Satu spec = satu topik aksi yang bisa dijalankan berurutan tanpa henti `[KEPUTUSAN 2026-09-29]`.** Digabung kalau topiknya sama, akun/role/entity sama, tidak butuh hardware, dan tidak mencampur pembuat data dengan bukan pembuat data. Permukaan yang berbeda tidak menghalangi penggabungan. **Topik aksi yang berbeda dan masing-masing butuh kondisi data yang bervariasi dipisah walau akunnya sama**: Delete, Toggle Active, dan Remove Access adalah tiga spec. Topik yang berbagi dataset yang sama tetap satu spec (contoh: Search, Filter, Sort, Pagination, dan Download di List). `[KEPUTUSAN 2026-10-21]` Ukuran sah memisahkan topik satu dataset bila gabungannya melewati batas ukuran jauh; sebaliknya, topik satu dataset yang tetap digabung (atau dipertahankan terpisah) menulis alasannya di `## Notes`, termasuk kegagalan keras satu blok yang membuat blok lain kehilangan makna.
2. **Screening (tanpa aksi) selalu di awal spec**, sebelum aksi lanjutan.
3. **Urutan di dalam sesi:** screening, lalu validasi yang diblokir (tidak membuat data), lalu aksi yang berhasil, lalu verifikasi di list.
4. **Variasi dari topik yang sama berurutan** (contoh: pilihan akses modul GS, FAMS, lalu entity lain).
5. **Aksi yang menghabisi atau merusak data (Delete, Bulk Delete, cascade purge, dan sejenisnya) selalu ditaruh paling akhir**, kalau spec yang sama masih punya blok aturan lain yang butuh baris itu tetap ada. Data yang sudah dihapus tidak bisa dipakai blok setelahnya, jadi aksi itu ditunda sampai semua blok lain selesai, walau PRD menyebutkannya lebih awal. Bonusnya, aksi ini di ujung sering sekaligus jadi cleanup untuk data seeding lain di spec yang sama.
6. **Kasus menutup form di akhir spec.** Menutup dalam keadaan dirty memakai form yang sudah dirty dari validasi, jadi tidak butuh buka tambahan. Menutup dalam keadaan bersih butuh form baru, jadi menjadi buka ulang terakhir. Form yang sudah diisi lalu dikosongkan lewat `[Clear Field]` tidak dihitung bersih untuk keperluan isolasi: kasus menutup bersih memakai form baru. Ini hanya soal isolasi state; dialog `Unsaved Changes` mengikuti PRD (form Create yang kosong tidak dirty, jadi menutupnya tidak memunculkan dialog). Pengecualian: blok yang memang menguji pengosongan atau revert itu sendiri (contoh: kembali ke nilai tersimpan) boleh melanjutkan form yang sama. Jumlah minimal buka form sama dengan jumlah kejadian yang menutup form.
7. **Tiap validasi diakhiri submit yang diblokir** dan pengecekan tidak ada data tercipta. Satu submit valid di akhir bila memang perlu membuat data.
8. **Pakai fitur yang menghemat**, contohnya checkbox "Stay on this form after submitting" supaya beberapa create terjadi dalam satu sesi modal tanpa membuka ulang.
9. **Nilai batas atau nilai khusus** ditempel ke create yang assert-nya tidak bentrok. Satu nilai khusus per field per user, supaya penyebab kegagalan jelas.
10. **Aturan yang klausanya terbelah lintas spec** (contoh: sisi Client dan sisi Principal, atau klausa presence dan absence) dikutip `sourceRules` kedua spec, dan `## Notes` kedua spec menulis butir "Pembagian klausa lintas spec" yang menyebut ID aturan, klausa, dan nomor spec masing-masing (S-01) `[KEPUTUSAN 2026-11-03]`.
11. **Select All lalu Bulk Delete masuk ke spec Delete, di akhir spec `[KEPUTUSAN 2026-09-29]`.** Aksi ini menghapus semua user di environment kecuali Default User dan akun yang login, termasuk user seeding milik spec lain. Karena itu spec Delete wajib berjalan sesudah spec lain selesai dan tidak paralel dengannya. Runner belum terbukti mengikuti nomor folder, jadi cara memisahkannya (suite atau tahap run sendiri) diputuskan di tahap script.
12. **Blokir karena kondisi data dipisah menjadi spec sendiri per topik `[KEPUTUSAN 2026-09-29]`.** Kasus yang ditolak sistem karena kondisi data target (contoh: TAG sudah dipasang user lain, Resend masih dalam cooldown, Reset Authenticator pada user yang belum enrolled, kuota atau batas seleksi tercapai) butuh data prasyarat khusus yang berbeda dari alur normal, sehingga tidak digabung dengan alur normal. Yang tetap digabung dengan alur normal adalah validasi field (wajib, format, panjang, duplikat) dan blokir berbasis identitas atau role (Default User, akun sendiri, target Total Control), karena tidak butuh data khusus. Aksi yang tidak punya blokir data tidak perlu spec blokir: `USER-LOGIC-05` menetapkan Deactivate, Remove Access, dan Delete selalu warn lalu proceed.

13. **Kelas harness yang berbeda dipisah, walau layar dan topiknya sama `[KEPUTUSAN 2026-10-08]`.** Asal: `gap-spec/gap-spec.md` (MFA, ActivityLog, Division, LoginPassword, Role, ResetPassword), pola yang sama berulang di 6 modul. Spec screening atau fungsional biasa tidak boleh memuat blok aturan dari kelas berikut; tiap kelas jadi spec sendiri:
    - **a. Defense-in-depth:** injeksi SQL/XSS, direct API tampering atau 403, manipulasi token, bypass server-side (token dibuang dari payload).
    - **b. Fault injection / resilience:** HTTP 5xx, timeout, outage penyedia (reCAPTCHA, IdP), rollback DB. Menahan respons hanya untuk mengamati state UI (loading, saving, spinner) bukan kelas b dan boleh berada di spec fungsional; yang masuk kelas b adalah kegagalan atau timeout yang dipaksakan. `Mode: mock` bila seluruh API di-mock; intercept parsial di atas backend nyata atau asersi state backend → `FE+BE` dengan intercept (bagian 6); kegagalan sisi server atau penyedia yang tidak bisa di-intercept tetap `FE+BE`.
    - **c. Multi-konteks:** multi-tab atau device, race antar-sesi, dua tenant, dua admin, flood rate-limit (429).
    - **d. Harness eksternal:** polling mail-catcher, decode QR, hardware biometrik, SSO IdP, time-travel atau TTL, background job. Membaca email di mail-catcher dan mengatur jam untuk menunggu countdown/cooldown (bagian 6) adalah langkah rutin spec fungsional dan tidak memicu pemisahan kelas d; yang masuk kelas d adalah spec yang objek ujinya harness itu sendiri (isi, waktu, dan template email; TTL sebagai batas yang diuji; teknologi bantu seperti screen reader dan ARIA live yang diamati keluarannya) `[KEPUTUSAN 2026-10-13]`.
    - **e. Volume data khusus:** kuota Selection Limit, data ≥ N record, retensi lintas tahun (perluasan prinsip 12). Ambang: hanya volume yang tidak lazim dihasilkan seed rutin (≥ 100 baris, 5.000 atau 5.001 baris) yang masuk kelas e; kebutuhan di bawah itu ditulis di Prerequisites tanpa memisah spec `[KEPUTUSAN 2026-10-21]`
    - **f. Binary buffer:** isi file CSV/XLSX (nilai sel, BOM, tipe sel) dipisah dari kegagalan ekspor. Nama berkas, nama kolom (header), dan jumlah baris adalah asersi fungsional dan boleh berada di spec fungsional `[KEPUTUSAN 2026-10-30]`.
    - **g. Asersi absence** ("baris log TIDAK muncul") dipisah dari asersi pencatatan (Status/Note spesifik). Pengecekan isolasi log per aktor ("entri aktor A tidak muncul di System Log aktor B") adalah asersi kepemilikan log, bukan kelas g, dan boleh berada di spec pencatatan. Asersi jumlah ("tepat 1 entri Delete per brand") bukan absence dan boleh berada di spec fungsional. Asersi scope exclusion (log modul atau produk lain tidak muncul di tab ini) dengan anchor positif dan data milik spec bukan kelas g dan boleh berada di spec fungsional `[KEPUTUSAN 2026-10-21]`
    - **h. State tenant:** write-lockdown (Client Suspended, Expired) dan perubahan plan tier dipisah dari verifikasi baca murni `[KEPUTUSAN 2026-10-21]`.

    **Cara menggabung antar-aksi:** kelas ringan (a tanpa harness eksternal, b) cukup satu spec per kelas per modul, misalnya satu spec "Resilience" untuk Create, Edit, Delete, dan Export, selama tidak melewati batas smell. Tidak perlu satu spec per aksi, karena tiap spec menambah login, hook, dan cleanup. Kelas berat (c, d, e) satu spec per jenis harness: mail-catcher tidak digabung dengan multi-tab, dan multi-tab tidak digabung dengan dua tenant.
    Setup Column, Bulk Action Bar, dan Search/Filter/Sort tetap satu spec selama dataset dan harness-nya sama; pecah hanya kalau melewati batas kelas di atas atau bagian sesudahnya tidak lagi bermakna bila bagian sebelumnya gagal keras (batas ukuran di bawah).
    **Pengecualian `[KEPUTUSAN 2026-10-13]`:** sebelas pengecualian berikut sah (`P-10` tidak dipakai di alur ini). Tiap spec yang memakainya menulis satu butir di `## Notes` yang menyebut id persis (`P-1`, `P-2`, `P-3`, `P-4`, `P-5`, `P-6`, `P-7`, `P-8`, `P-9`, `P-11`, atau `P-12`, bukan "prinsip 13") beserta alasannya.
    - **P-1, state berat:** blok aturan yang konteksnya bergantung pada state berat yang baru dibangun langkah sebelumnya di spec asal (contoh: lock tahap 1 jam, handoff MFA, kuota Resend habis) boleh tetap di sana, termasuk klausa absence kelas g milik aturan itu. Seeding berat yang sama dengan aksi aturan (mis. Division in-use yang dibangun lewat Login User seeding) termasuk state berat bagi asersi absence yang berasal dari aksi yang sama. Asersi absence yang tidak butuh state berat tetap dipindah ke spec absence. `[KEPUTUSAN 2026-11-03]` State yang dapat dibuat lewat satu panggilan API atau fixture BE (mis. label dihapus lewat API) bukan state berat.

## 3a. Role Matrix `[KEPUTUSAN 2026-09-29]`

Kasus izin per role dipisah menjadi spec **positif** dan spec **negatif** untuk tiap aksi. Satu spec dijalankan untuk banyak role, karena langkahnya identik dan hanya akun login yang berbeda. Daftar role dan akunnya ditulis di `## Prerequisites` sebagai tabel "Role yang diuji" (akun dirujuk lewat `DU-nn`, bagian 5), dan langkah spec berbunyi "lakukan langkah berikut untuk setiap role pada tabel".

- **Spec positif:** aksi berhasil. Role yang diuji adalah Total Control dan role spesifik yang berhak atas aksi itu.
- **Spec negatif:** aksi tidak tersedia (Hidden atau Disabled, atau ditolak 403). Role yang diuji adalah Read Only dan role yang tidak berhak atas aksi itu.
- Kasus yang bukan soal "aksi ditolak" (sidebar tersembunyi, direct URL 403, landing state, target yang terlindungi seperti Default User dan Self) dikelompokkan sebagai spec negatif tersendiri per topik.
- **Matriks visibilitas per role** (satu daftar elemen, banyak role, hasil berbeda per role) adalah spec Role Matrix sendiri dan boleh memuat kedua polaritas (tampil dan Hidden/Disabled). Beri title tanpa kata "Positif" atau "Negatif" (contoh: "Role Matrix: Visibilitas Elemen Tab Brand per Role"); `caseType` mengikuti bagian 8.
- **Sumber kombinasi role × aksi `[KEPUTUSAN 2026-11-03]`:** hanya kombinasi yang dinyatakan PRD yang ditulis: baris matriks role atau visibilitas (PRD §2, §4.8, §9.x; ID sintetis `<PFX>:<table-slug>/<row-key>`) atau aturan ber-ID yang menyebut role. Satu baris matriks = satu aturan di `sourceRules`. Kombinasi yang tidak dinyatakan PRD dicatat sebagai "Temuan PRD" (S-15), bukan dikarang di spec.
- Cara skrip menjalankan banyak role (perulangan di dalam satu `it()` atau beberapa kali run dengan akun berbeda) diputuskan di tahap script.
- **Susunan spec Role Matrix `[KEPUTUSAN 2026-09-29]`:** satu spec per aksi dengan positif dan negatif terpisah, karena lebih partikular. Perulangan "untuk setiap role pada tabel" dipakai hanya bila langkah tiap role identik; bila langkahnya berbeda per role, spec ditulis per blok role. `[KEPUTUSAN 2026-10-21]` `[KEPUTUSAN 2026-10-30]` Spec ditulis per blok role juga sah bila langkah tiap role identik tetapi ganti akun menuntut Step eksplisit (akun pertama login di hook `before`); `## Notes` menyebut alasannya. `[KEPUTUSAN 2026-11-02]` Satu spec Role Matrix boleh memuat beberapa aksi bila alasannya ditulis di `## Notes`; polaritasnya harus seragam (aturan positif dan aturan negatif tidak dicampur dalam satu spec, kecuali matriks visibilitas di atas).

## 5. Data Uji `[KEPUTUSAN 2026-11-03]`

Data uji tinggal di repo e2e, satu file per suite: `docs/data/<Suite>.md`, dengan `<Suite>` = `<Group><SubModul>` (nama dasar sama dengan halaman coverage, contoh `docs/data/AdminConsoleSettingsDeviceSku.md` berpasangan dengan `docs/coverage/AdminConsoleSettingsDeviceSku.md`). File ini ditulis pemilik rencana dari bagian `## Data uji` rencana yang disetujui.

- **Format.** Baris pertama sesudah judul menyebut PRD inti sumber (path dan 16 hex pertama sha256), lalu satu tabel:

  ```
  | ID | Data | Nilai | Sumber | Lifecycle | Dipakai spec |
  |---|---|---|---|---|---|
  | DU-01 | Akun Total Control Admin Console | env AC_TC_EMAIL, AC_TC_PASSWORD | PRD §2 matriks role | pre-setup | 001, 004 |
  | DU-02 | Brand Population 12 baris | Apex Tools … Linear Dynamics | PRD §4.1.2 Example Data | pre-setup | 003 |
  | DU-03 | Name batas 120 karakter | (pengisi + suffix `{runId}-<NNN>`) | ACDS:V-03 | dinamis | 005 |
  ```

- **ID stabil.** `DU-01`, `DU-02`, … urut per suite, tidak pernah di-renumber dan tidak pernah dipakai ulang. Baris yang tidak dipakai spec mana pun lagi dihapus; ID-nya tidak diberikan ke data lain.
- **Kolom Sumber** hanya salah satu dari: blok Example Data PRD (`PRD §4.1.x Example Data`), ID aturan PRD (persis seperti rules JSON, mis. `ACDS:V-03`, untuk nilai batas atau nilai yang ditentukan aturan), matriks role PRD (`PRD §2 matriks role`, untuk akun), atau `turunan planner` untuk data yang tidak diberikan PRD (akun tambahan, volume populasi, data dinamis). Baris `turunan planner` hanya sah bila tercantum di rencana yang disetujui di gate; kebutuhan baru sesudah gate kembali ke gate, bukan ditambahkan penulis.
- **Kolom Lifecycle** hanya salah satu dari: `pre-setup` (sudah ada di environment sebelum run, disediakan fixture atau seed environment, dibaca bersama), `dinamis` (dibuat hook spec per run lewat API, bersuffix per run), atau `dibuat spec NNN` (dibuat oleh langkah spec NNN itu sendiri sebagai objek uji). Data `dibuat spec NNN` tidak dipakai spec lain.
- **Kolom Dipakai spec** berisi nomor spec (`NNN`) yang merujuk baris itu; harus cocok dengan rujukan di spec.
- **Spec merujuk data hanya lewat `DU-nn`.** `## Prerequisites` mendaftar setiap `DU-nn` yang dipakai langkah (tidak ada yang tidak dipakai, tidak ada yang kurang, S-11), dan langkah menulis `DU-nn` sebagai nilai (contoh "Ketik Name `DU-07`"), bukan nilai mentah. Teks UI (toast, label, pesan) bukan data uji; teks itu berasal dari klausa PRD (S-02). `check-suite-prd.py` T9 melaporkan `DU-nn` di spec yang tidak ada di file data.
- **Akun.** Email dan password akun lewat env var `<PREFIX>_<ROLE>_EMAIL` dan `<PREFIX>_<ROLE>_PASSWORD`; kolom Nilai menyebut nama env, tidak pernah password literal. Akun yang tidak diturunkan dari matriks role PRD adalah baris `turunan planner`.
- **Fixture.** Data `pre-setup` disediakan lewat fixture `fixtures/<modul>.json` di tahap script. Isinya identitas data, bukan rahasia.
- **Password dan token tidak boleh masuk fixture, file data, atau spec** (semua file di git). Simpan di environment variable lewat `executionConfig.environmentVariables` dan akses lewat `Spectra.env.NAMA`. `[REKOMENDASI]`, perlu keputusan tim tentang cara distribusinya.
- **Penamaan env var `[KEPUTUSAN 2026-10-08]`:** env akun aktor dipakai lintas suite dan tidak berprefix modul: `<APP>_<ROLE>_PASSWORD` dan `<APP>_<ROLE>_EMAIL` (contoh `GS_TC_PASSWORD` untuk Total Control Global Settings, `AC_TC_PASSWORD` untuk Total Control Admin Console); `<PREFIX>` pada butir Akun adalah `<APP>` ini. Password uji yang dipasang ke user dinamis berprefix kode modul: `<MODUL>_PASSWORD`, varian nilai lain diberi akhiran (`_ALT`, `_72`, `_SPECIAL`), contoh `ACT_PASSWORD_72`. Input uji kebijakan yang submit-nya diblokir tetap baris DU, dan nilainya boleh literal di file data. Setiap nama baru didaftarkan di `executionConfig.environmentVariables` (`spectra.config.ts`, nilai dari `process.env`) dan di `.env.example`. Nilai diisi di `.env` lokal (di-ignore git) atau secret CI, lalu di-export sebelum run (contoh `set -a; . ./.env; set +a`); runner tidak terbukti membaca `.env` sendiri. Password salah untuk skenario login gagal memakai `Spectra.env.LP_PASSWORD_WRONG`, bukan literal `[KEPUTUSAN 2026-10-21]` `[KEPUTUSAN 2026-10-30]` Nama env akun aktor yang memuat kode modul atau entitas (contoh `GS_GSET_RO_PASSWORD`, `GS_NEWCLIENT_TC_PASSWORD`) sah bila nama `<APP>_<ROLE>_PASSWORD` sudah terdaftar untuk akun lain di suite lain; satu nama hanya punya satu arti, dan setiap nama didaftarkan di `executionConfig.environmentVariables` dan `.env.example`.
- **Data dinamis harus unik per run.** Nilai yang harus unik (email, employee ID) dibuat dengan suffix acak atau timestamp. Kalau tidak, run kedua gagal karena data sudah ada. Suffix memuat nomor spec juga, `+{runId}-<NNN>` (contoh `budiaditya+{runId}-009@qwertysystem.net`) `[KEPUTUSAN 2026-10-08]`, supaya dua spec yang men-seed nama dasar yang sama tidak bentrok dalam satu run. `{runId}` hanya terdiri atas digit (timestamp) supaya kata kunci pendek di data uji tidak cocok dengan sufiks `[KEPUTUSAN 2026-10-21]`
- **Lifecycle lintas spec dipecah.** Setiap spec membuat datanya sendiri (lewat API di `before` atau `beforeEach`) dan tidak menumpang hasil spec lain, walau alur PRD menyebut data yang dibuat di satu fungsi lalu diedit dan dihapus di fungsi lain.
- Data prasyarat sebisa mungkin dibuat lewat API, bukan lewat UI, supaya cepat dan tidak ikut gagal saat UI yang bukan fokus berubah.
- **Sesi API aktor `[KEPUTUSAN 2026-10-30]`:** login API (password) untuk akun yang sama dengan sesi UI memakai token yang tidak dihitung sebagai sesi web, sehingga batas satu sesi web tidak terpengaruh dan sesi UI tidak diusir. Kemampuan itu disediakan tim BE/FE dan dinyatakan sekali di `suite.md`; `## Prerequisites` spec merujuknya dengan satu baris.
- Data yang dibuat spec dibersihkan di `afterEach` atau `after`, dan tulis pembersihan sehingga tidak berasumsi setup berhasil penuh (aturan cascade hook).

## 6. Real Backend vs Mock

- Alur normal (happy path, validasi, permission) memakai backend asli `[REKOMENDASI]`.
- `Spectra.intercept()` untuk kondisi yang tidak bisa dipicu dengan aman di backend nyata: error 500, timeout, dan response lambat. Kasus seperti ini tetap ditulis sebagai spec, dengan `Mode: mock` dan kebutuhan mock-nya di Prerequisites.
- `Mode: mock` hanya untuk spec yang seluruh API-nya di-mock (dijalankan tim FE sebagai integration test, tanpa backend nyata) `[KEPUTUSAN 2026-10-08]`. Spec yang memaksa sebagian respons lewat `Spectra.intercept()` di atas backend nyata, atau yang mengasersi state backend (status token, status user, data di layar lain), ditandai `FE+BE` dengan kebutuhan intercept tetap ditulis di Prerequisites. Intercept hanya untuk respons HTTP yang bisa di-intercept di browser. Kegagalan di sisi server atau penyedia eksternal (flood rate-limit 429, email provider mati atau bounce, jam server digeser) tetap `FE+BE`. Pemicunya ditulis sebagai langkah eksplisit, kemampuan teknisnya tercantum di Prerequisites, dan pemulihan state (provider, jam, counter rate-limit) dilakukan di hook `after` yang tetap jalan walau spec gagal di tengah.
- **Manipulasi jam `[KEPUTUSAN 2026-10-13]`:** aturan yang menunggu waktu (countdown 60 detik, cooldown 10 menit, TTL, kuota 24 jam) dipenuhi dengan mengatur jam, bukan menunggu. Prerequisites menyebut jam mana yang diatur: jam server, jam browser/klien, atau keduanya (countdown UI berjalan di jam klien, jadi memajukan jam server saja tidak mengaktifkan `[Resend code]`). Untuk batas eksak ("tepat 5:00", "4:59"), jam server diset absolut ke waktu terbit kode + N detik atau dibekukan, bukan digeser relatif, karena detik nyata sejak request tidak dihitung. Jam server dan jam browser/perangkat diatur bersama, kecuali TTL yang dihitung murni di server dan tidak diamati lewat UI (contoh: umur kode 5 menit, kuota 24 jam); bila hanya jam server yang dimajukan, jam itu dipulihkan sebelum asersi countdown UI dan sebelum bagian spec berikutnya yang memakai jam bersama. Menunggu waktu nyata hanya untuk jeda pendek (±30 detik) yang disebut eksplisit di Prerequisites. Di atas jeda nyata ±30 detik hanya lewat idiom baku "polling worker commit" (muat ulang halaman tiap 5 detik sampai banner atau notifikasi muncul, batas 2 menit) atau kueri fixture status job; klausa yang menunggu lebih dari 30 detik ditulis memakai 5 detik SSE atau 30 detik nyata `[KEPUTUSAN 2026-10-30]`. Untuk nilai Date berketelitian menit yang harus berbeda (asersi sort Date), hook boleh menunggu sampai menit berganti (maksimum 60 detik) dan hal itu disebut di Prerequisites `[KEPUTUSAN 2026-10-22]`. Satu penantian hanya memisahkan dua kelompok seed; bila asersi sort Date membutuhkan lebih banyak nilai Date yang berbeda, asersi dibatasi pada pasangan entri yang berbeda menit (urutan entri se-menit tidak diasersi), bukan menunggu menit berganti berkali-kali `[KEPUTUSAN 2026-11-02]`. Batas eksak berlaku juga untuk umur token (contoh: tepat 90 hari): jam server diset absolut ke waktu terbit token + N, bukan digeser relatif. Pengecualian: aturan yang mensyaratkan dialog Session Expired belum tampil walau sesi stale memajukan hanya jam server dan memulihkannya sebelum aksi berikutnya `[KEPUTUSAN 2026-10-13]`. Suite yang mengubah state global (jam, counter rate-limit per IP, versi Privacy Policy, Geo-IP, lokasi koneksi) berjalan serial (`parallel: false`), hal itu ditulis di `## Prerequisites` spec yang bersangkutan (bukan hanya di Notes atau `suite.md`), dan hook `after` memulihkan state-nya. Bila PRD menetapkan bahwa countdown dihitung dari timestamp server dan bertahan setelah refresh, itu menjadi dasar asersi persistensi, tetapi tidak menyatakan jam mana yang dibaca penghitung mundur di UI; karena itu jam server dan jam browser tetap diatur bersama.
- **Readback respons mock `[KEPUTUSAN 2026-10-21]`:** pada spec `Mode: mock`, asersi yang hanya membaca ulang isi respons mock list ditulis bila klausa aturan memintanya, bukan diturunkan dari efek yang tidak dinyatakan aturan.
- **Resilience `Mode: mock` `[KEPUTUSAN 2026-10-29]`:** pengecualian atas aturan state backend di atas. Spec resilience (5xx, timeout, koneksi terputus) boleh `Mode: mock` bila hanya mengasersi perilaku FE atas respons mock (toast, popup, bar dan seleksi, switch, isi list hasil baca ulang respons mock). Klausa yang membutuhkan state server nyata (nilai tersimpan di server, data di layar lain seperti Detail User, "kondisi terkini dari server", "tetap ada setelah dimuat ulang") tidak ditulis di spec mock itu: klausa itu diasersi di spec FE+BE terpisah yang di-intercept di atas backend nyata, dan kedua spec mengutip aturan yang sama (prinsip 10). Pengecualian ini hanya untuk resilience, tidak untuk spec mock lain.
- **Jendela amat SSE `[KEPUTUSAN 2026-10-30]`:** asersi absence atas propagasi SSE atau antar-tab ("tidak ada dialog", "tampilan tidak berubah", "tidak menerima event") didahului langkah penghubung "Tunggu 5 detik tanpa memuat ulang halaman" tanpa `Verifikasi`. Lima detik adalah jendela standar; `## Prerequisites` menyebutnya sebagai pilihan spec (bukan nilai PRD) sampai PRD menyatakan durasinya. `[KEPUTUSAN 2026-11-02]` Asersi absence atas notifikasi in-app (Notification Center) memakai jendela yang sama, "Tunggu 5 detik tanpa memuat ulang halaman", dinyatakan di `## Prerequisites` sebagai pilihan spec, didahului anchor positif yang membuktikan pengiriman notifikasi.
- Target environment untuk e2e (staging, lokal, atau lainnya) belum ditentukan. Sementara `spectra.config.ts` masih menunjuk ke demo app bawaan.

## 8. Traceability dan Coverage

Setiap spec punya frontmatter:

```yaml
id: TC-GS-USER-E2E-001-create-user-happy-path
title: <judul, sama persis dengan it()>
priority: Critical | High | Medium | Low
caseType: Positive | Negative | Edge
status: draft | ready-for-automation | automated | deprecated
sourceRules:
  - ACDS-LOGIC-01a
  - F-ACDS-02a1
  - ACDS:V-03
coverage:
  web: automated
```

**Format ID di `sourceRules` `[KEPUTUSAN 2026-11-03]`:** ID ditulis persis seperti rules JSON.
- ID yang sudah berprefix modul ditulis apa adanya: `ACDS-LOGIC-01a`, `F-ACDS-02a1`, `F-ACDS-02.k1`.
- ID lokal tanpa prefix modul dikualifikasi dengan prefix modul dan titik dua: `ACDS:V-03`, `ACDS:FLD-01`, `ACDS:D-02`, `ACDS:T-04`, `ACDS:S-07`, `ACDS:EC-12`, `ACDS:DO-03`, `ACDS:FI-05`. PRD tidak diubah.
- Baris matriks tanpa ID (Setup Column, matriks role atau visibilitas, butir "Must NOT") memakai ID sintetis yang dihitung harness: `ACDS:<table-slug>/<row-key>` dan `ACDS:must-not/<item-slug>`.
- Hanya ID leaf yang dikutip (T3); ID induk tidak dikutip. ID yang tidak ada di rules JSON tidak dikutip (T2). ID aturan yang pensiun atau berganti nama terdeteksi lewat snapshot inventaris ID per audit, bukan lewat changelog PRD.

**Prioritas dan caseType dari aturan `[KEPUTUSAN 2026-11-03]`:**

| Sumber | Frontmatter spec |
|---|---|
| Aturan dengan induk fungsi `F-` di PRD §9.1: Prioritas P0 / P1 / P2 / P3 | Critical / High / Medium / Low |
| Aturan tanpa induk `F-` | Medium (P2) |
| Spec, `priority` | prioritas tertinggi di antara aturan `sourceRules` (T6) |
| Aturan validasi (`V-`), kondisi (`.kN`), butir "Must NOT" | Negative |
| Aturan edge case (`EC-`) | Edge |
| Aturan lain (`F-`, `LOGIC`, `D-`, `FLD-`, `T-`, `S-`, `DO-`, `FI-`, `O-`, ID sintetis matriks) | Positive |
| Spec gabungan, `caseType` | ikut jenis alur utama yang dominan (lihat di bawah) |

Rules JSON memuat prioritas dan caseType tiap aturan hasil pemetaan ini; penulis menyalinnya, tidak menghitung ulang.

**Aturan `caseType` untuk spec gabungan `[KEPUTUSAN 2026-09-26]`:** satu spec hanya punya satu `caseType`, dipilih dari jenis alur utama yang dominan, yaitu tujuan akhir alur spec tersebut, bukan jenis tiap aturan sumber. Contoh: spec yang mengecek error tanggal kosong lalu berujung sukses membuat user berjenis `Positive`; spec yang seluruhnya menguji penolakan input berjenis `Negative`; spec yang seluruhnya menguji batas nilai atau karakter berjenis `Edge`. Kalau tidak ada yang dominan, pilih caseType aturan dengan prioritas tertinggi.

**Arti `coverage` `[KEPUTUSAN 2026-09-26]`:** kolom `coverage.web` hanya menyatakan jenis pengujian di platform itu (`automated`, `manual`, atau `unsupported`), bukan progres. Spec yang dirancang untuk otomasi memakai `automated` sejak `draft`. Progres pengerjaan dibaca dari `status`, bukan dari `coverage`.

**Platform lain `[KEPUTUSAN 2026-10-13]`:** `coverage.mobile` memakai nilai yang sama (`automated`, `manual`, `unsupported`) dan hanya ditulis pada spec yang berjalan di aplikasi mobile; spec web saja cukup `coverage.web`. Perangkat atau emulator yang dibutuhkan ditulis di `## Prerequisites`.

**Spec mobile yang membaca log lewat web `[KEPUTUSAN 2026-10-13]`:** spec yang berjalan di aplikasi mobile tetapi memakai Browser Admin atau Browser License untuk membaca log atau Concurrent User memakai `coverage.web` dan `coverage.mobile` keduanya `automated`; perangkat dan browser yang dibutuhkan ditulis di `## Prerequisites`.

Field `status`: `draft` saat spec.md selesai, `ready-for-automation` setelah direview QA, `automated` setelah `web.test.ts` lulus lint dan lulus dijalankan.

**Halaman coverage `[KEPUTUSAN 2026-11-03]`:** `docs/coverage/<Suite>.md` ditulis pemilik rencana, tabelnya diturunkan dari frontmatter spec dan rules JSON (tidak diedit tangan sebagian). Formatnya persis:

  ```
  # Coverage <Group><SubModul>

  Sumber: `<path PRD inti>` · PRD sha256 `<16 hex pertama>` · <N> aturan leaf · <M> spec

  ## Aturan → spec
  | Aturan | Spec | Mode |
  ## Di luar E2E
  | Aturan | Alasan | Rujukan tc-backend |
  ## Ditahan
  | Aturan | Temuan | Catatan |
  ## Tidak berlaku
  | Kewajiban | Alasan (rujukan PRD) |
  ## Spec
  | Spec | Mode | Langkah | Aturan |
  ## Catatan
  ```

- `<N>` = jumlah semua aturan leaf di rules JSON, termasuk kewajiban turunan (dikutip, di luar E2E, ditahan, dan tidak berlaku); `<M>` = jumlah folder spec di suite. PRD sha256 = 16 hex pertama sha256 PRD inti saat halaman ditulis.
- **Aturan → spec:** satu baris per aturan yang dikutip; kolom Spec mendaftar ID semua spec yang mengutipnya, kolom Mode `FE+BE`, `mock`, atau keduanya (nilai baris `Mode:` spec, bagian 2).
- **Di luar E2E:** satu baris per aturan; Alasan salah satu dari tiga alasan bagian 2, tidak kosong; Rujukan tc-backend berisi ID case `tc-[modul]-backend.md` (contoh `TC-ACDS-BE-041`) bila ada, atau `-`. Aturan di tabel ini tidak dikutip spec mana pun (T4).
- **Ditahan:** satu baris per aturan ditahan; Temuan berisi ID temuan (`IGAP-0012`, `DEP-3`) atau `baru: <ringkasan>` untuk Temuan PRD yang belum tercatat (S-15); Catatan bebas. Aturan di tabel ini tidak dikutip spec mana pun (T5).
- **Tidak berlaku:** satu baris per kewajiban turunan (`<PFX>:obl/...`) yang dikesampingkan PRD; Alasan memuat rujukan `L<n>` atau § PRD. Kewajiban di tabel ini tidak dikutip spec mana pun (T11).
- **Spec:** satu baris per spec (ID spec lengkap, sama dengan nama folder); Langkah = jumlah langkah bernomor; Aturan = daftar ID di `sourceRules` spec itu.
- **Catatan:** keterangan suite (Temuan PRD lintas spec, ketergantungan run serial), tanpa narasi proses.

`spectra lint` **tidak** memvalidasi isi `sourceRules`; keterlacakan diperiksa `check-suite-prd.py` (T1 sampai T8).

## 8b. Aturan Penulisan Langkah dan Asersi

Berasal dari audit Account Activation (2026-10-08) dan audit sesudahnya. Ditulis sebagai aturan supaya generate berikutnya tidak mengulang temuan yang sama.

1. **Request langsung ke server `[KEPUTUSAN 2026-10-08]`.** Langkah yang mengirim request lewat klien HTTP atau fixture BE tidak melewati browser. Asersinya hanya respons server (status) dan state data (diperiksa lewat fixture BE). Pengalihan halaman, toast, atau tampilan tidak diasersi di spec itu; perilaku FE untuk respons yang sama diasersi di spec jalur form. Kalau aturan PRD mengharapkan perilaku FE pada request langsung, jangan ditulis: catat sebagai "Temuan PRD" (S-15).
2. **Asersi absence punya anchor positif `[KEPUTUSAN 2026-10-08]`.** Verifikasi "tidak ada entri/pencatatan/log" didahului langkah `Verifikasi` yang membuktikan sesuatu yang seharusnya ada di surface yang sama sudah tampil (entri milik modul lain, pesan penolakan, jumlah awal yang dicatat), dan surface-nya disebut satu per satu. Anchor harus terhubung ke pemicu; pemicu yang tidak menyentuh entitas anchor memakai surface agregat (jumlah total sebelum dan sesudah). `[KEPUTUSAN 2026-10-21]` Aturan yang sama berlaku untuk absence data di tabel, dropdown, atau card (tidak ada baris, opsi, atau card): didahului `Verifikasi` yang membuktikan data pembanding pada surface yang sama sudah tampil (baris atau opsi lain), supaya hasil kosong bukan karena surface belum dimuat atau pencarian salah ketik. Untuk "baris hilang" sesudah Delete atau Bulk Delete yang toast suksesnya sudah diasersi, toast sukses itu menjadi anchor (respons server selesai dan daftar di-refresh); baris pembanding tidak wajib. Toast hasil server yang sudah diasersi (sukses atau netral) juga menjadi anchor absence baris sesudah Edit `[KEPUTUSAN 2026-10-22]`. Absence sesudah muat ulang `F5` didahului `Verifikasi` elemen lain pada halaman itu tampil `[KEPUTUSAN 2026-10-22]`. Anchor yang sah untuk absence sesudah muat ulang, navigasi, atau Detail adalah satu `Verifikasi` elemen lain pada halaman itu tampil (Breadcrumb, `[?]`, Metric Cards, Dropzone, dan sejenisnya) dan elemen anchor itu dinyatakan PRD untuk halaman tersebut; hover atau pemicu cukup sebagai anchor tooltip; "daftar saran kosong" combobox bukan anchor `[KEPUTUSAN 2026-10-30]`. Absence item menu atau sidebar didahului `Verifikasi` item menu lain pada sidebar yang sama sudah tampil. `[KEPUTUSAN 2026-10-21]` Asersi universal ("setiap baris ...", "hanya baris ...") didahului `Verifikasi` yang membuktikan sedikitnya satu baris pembanding pada surface yang sama, supaya tabel kosong tidak meloloskan asersi; frasa "tabel (tetap) tersaring", "terfilter", atau "difilter" tanpa kuantor pada hasil Search atau Filter dihitung asersi universal, sehingga pembanding generik ditulis sebelum asersi pertama `[KEPUTUSAN 2026-10-22]`; pengecualiannya empty state di bawah. Pembanding ditulis generik ("sedikitnya satu baris") kecuali baris spesifik itu dijamin tampil oleh Search, sort, atau ukuran halaman yang dipakai `[KEPUTUSAN 2026-10-22]`. Asersi keadaan checkbox atau seleksi ("seluruh baris ter-uncheck", "seleksi 0") tidak memerlukan pembanding karena barisnya dibuktikan oleh aksi centang atas baris bernama pada blok yang sama `[KEPUTUSAN 2026-10-22]`. Empty state "No results found" yang diproses Search atau Filter adalah anchor positif yang sah untuk absence hasil Search. Untuk asersi `Hidden` elemen UI pada Role Matrix dan untuk "walkthrough tidak muncul", Table Tools atau halaman yang sudah termuat menjadi anchor permukaan; elemen UI diatur butir 11, bukan butir 2. `[KEPUTUSAN 2026-10-22]` Klausa "hanya X" mengasersi X tampil dan juga satu baris atau elemen lain yang dijamin ada tidak tampil; absence kolom atau field pada surface yang sudah termuat cukup didahului `Verifikasi` kolom atau field lain tampil `[KEPUTUSAN 2026-11-02]`.
3. **Boundary waktu dan time-travel `[KEPUTUSAN 2026-10-08]`.** Acuan waktu (T0) dibaca dari waktu terbit artefak (token, entri) lewat API seeding, bukan diperkirakan dari waktu hook atau waktu nyata saat langkah dijalankan. Jam server diset absolut ke `T0 + durasi`. Margin terhadap batas kurang dari 5 menit ditulis di Prerequisites beserta caranya dihitung.
4. **Rate limit `[KEPUTUSAN 2026-10-08]`.** Sebut endpoint yang dihitung, bahwa counter dipisah per endpoint bila begitu di sumber, dan payload flood yang tidak mengonsumsi state (misalnya body yang ditolak validasi) supaya verifikasi akhir tetap bermakna. Counter direset sebelum tiap blok.
5. **Asersi state sementara tepat waktu `[KEPUTUSAN 2026-10-08]`.** Fokus, tooltip, hover, Loading, dan state serupa diasersi sebelum langkah berikutnya yang mengubah state itu. ## 11. Konvensi Beku per Loop Modul, Hemat Token, dan Batas Putaran Audit `[KEPUTUSAN 2026-11-03]`

- **a. Keterlacakan 100% oleh script.** Keterlacakan PRD → spec (T1 sampai T5) seluruhnya diperiksa `check-suite-prd.py` terhadap rules JSON. Auditor tidak menurunkan ulang cakupan aturan, tidak menghitung ulang leaf, dan tidak membandingkan `sourceRules` dengan PRD secara manual; hasil script dipakai apa adanya.
- **b. Semua yang mekanis di script.** Setiap butir yang bisa diperiksa mesin (kode di bagian 10a dan di paragraf penutupnya) hanya diperiksa `check-suite-prd.py`; agen generate dan audit hanya menilai butir tanpa kode (judgment).
- **c. Daftar cek identik.** Generate dan audit memakai daftar yang sama (bagian 10, 10a, dan butir Lampiran A modul). Generate belum selesai sebelum `check-suite-prd.py` tanpa `[FINDING]` dan `spectra lint --strict` bersih; lead `[REVIEW]` sudah diperiksa dan hasilnya tercatat di laporan generate.
- **d. Fix pass memverifikasi dirinya.** Perbaikan hasil audit menjalankan `check-suite-prd.py` dan swa-periksa bagian 10 dan 10a atas spec yang diubah sebelum delta diminta. Delta tidak diminta selama script masih melaporkan `[FINDING]` pada spec yang diubah.
- **e. Beku per loop modul.** Satu loop modul = generate, audit penuh, perbaikan, dan delta-deltanya. Selama loop, dokumen ini, skill `e2e-prd-generate-spec`, skill `e2e-prd-audit`, dan `scripts/check-suite-prd.py` tidak diubah. Hash unit konvensi dan file itu dicatat di awal loop dan dicek sebelum laporan atau close-out; bila berubah, run berhenti dan melaporkan "konvensi berubah di tengah loop" alih-alih menggabungkan hasil dari dua versi aturan. Aturan baru atau aturan yang diubah berlaku sesudah loop ditutup, tidak pernah surut ke loop yang masih terbuka.
- **f. Slice audit kecil.** Tiap analis membaca spec di slice-nya secara penuh, indeks aturan, dan hanya baris aturan yang dikutip spec slice itu (ditambah baris data uji yang dirujuknya); PRD penuh tidak dibaca per slice.
- **g. Delta hanya yang berubah.** Delta membaca hanya spec yang hash-nya berubah dan aturan yang hash barisnya berubah terhadap snapshot audit penuh (bagian `## Rule rows` snapshot), ditambah temuan terbuka delta sebelumnya. Companion changelog PRD tidak pernah dibaca untuk mencari perubahan.
- **Usulan aturan di luar loop.** Pola yang menurut audit perlu aturan baru masuk "Perlu keputusan" sebagai usulan dan diterapkan dalam satu batch sesudah loop suite itu selesai, bukan di tengah perbaikan (butir e). Suite yang sudah lulus disapu hanya bila diminta, lewat `check-suite-prd.py` atau grep.
- **Perbaikan terbatas.** Perbaikan hasil audit hanya menyentuh spec yang punya temuan Berat atau Sedang (temuan Ringan di spec yang sama boleh ikut), serta file data uji dan halaman coverage bila temuan menyentuhnya. Spec lain tidak disentuh, termasuk perapian massal, supaya delta berikutnya cukup memeriksa spec yang berubah.
- **Batas putaran.** Temuan Ringan dan "Temuan PRD" tidak memicu putaran audit baru; "Temuan PRD" diteruskan ke `prd-internal-gap-check` / `prd-gap-solve`. Satu audit penuh diikuti paling banyak dua delta; sisa Berat atau Sedang sesudah delta kedua diserahkan ke pemilik proses sebagai keputusan (terima dan catat, atau audit penuh baru).
- **PRD berubah di tengah loop.** Hash PRD di header coverage yang berbeda dengan PRD sekarang (T8) berarti spec perlu disinkronkan: rules JSON ditulis ulang, lalu hanya aturan yang hash barisnya berubah, aturan baru, dan aturan yang hilang yang ditangani (butir g).
